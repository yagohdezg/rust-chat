# rust-chat

A lean Rust + Postgres reimplementation of a LibreChat-style AI chat platform.
Streaming chat, multi-provider LLMs, agents with tools, MCP integration, and
isolated code execution — with a small, auditable Rust runtime instead of a
heavy Node stack.

The memory win comes from the Rust runtime and from offloading sandboxes to
isolated microVMs, **not** from the database. Postgres is kept for relational
integrity.

## Architecture

```
              ┌──────────────┐        SSE        ┌─────────────────┐
  Browser ───▶│  SvelteKit   │◀─────────────────▶│   chat-server   │
              │   (web/)     │   /api/chat       │  (axum + tokio) │
              └──────────────┘                   └────────┬────────┘
                                                          │
                       ┌──────────────┬───────────────────┼───────────────────┐
                       ▼              ▼                   ▼                   ▼
                  ┌──────────┐  ┌────────────┐     ┌────────────┐     ┌──────────────┐
                   │ Postgres │  │ providers  │     │   agents   │     │   sandboxd   │
                   │          │  │ OpenAI SSE │     │ tools/loop │     │   BoxLite    │
                  └──────────┘  └────────────┘     └─────┬──────┘     └──────┬───────┘
                                                         │                   │
                                                   ┌─────▼──────┐   ┌────────▼────────┐
                                                   │   chat-mcp │   │ BoxliteBackend  │
                                                   │ stdio RPC  │   │  (chat-sandbox) │

```

## Sandbox / code execution

Code generated by models is untrusted, so it runs in **BoxLite** — one
hardware-isolated microVM per run (own kernel, seccomp, cgroups, egress
allow-list) via a BoxLite REST server (`boxlite serve`). Requires KVM on the
host. Setting `SANDBOX_BACKEND=gvisor` instead runs each request in a gVisor
user-space-kernel sandbox locally with `runsc`: a cheaper middle tier between
the microVM and host execution that needs no KVM.

Execution is split across two processes:

- `chat-server` always talks to the standalone **`sandboxd`** service over HTTP
  (`HttpSandboxBackend`, `SANDBOXD_URL` + `SANDBOXD_TOKEN`). It holds no
  in-process backend and no sandbox spec.
- `sandboxd` owns the `SandboxSpec` (image, memory, CPU, timeout) from its
  environment and runs each request on the backend selected by `SANDBOX_BACKEND`
  (`boxlite`, the default, or `gvisor`). `SANDBOXD_TOKEN` is **mandatory**;
  `/v1/exec` requires `Authorization: Bearer` and `/health` is open.

Per run, `BoxliteBackend` creates a box, uploads `main.<ext>` and any input
files as an in-memory tar, streams stdout/stderr over the execution's WebSocket
attach, and force-deletes the box on every path (success, error and timeout).
Both the exec and the surrounding sequence carry a timeout, and each stream is
capped at 1 MiB.

### Code over your files

Every user has a personal file library. Uploading a file into a conversation
stores it in that library and attaches it to the conversation; a library file
can then be attached to any other conversation. When code runs — through the
`execute_code` tool, `POST /api/sandbox/run`, or `POST /api/computers/exec` —
the conversation's attached files are materialized into the box's `/app`
directory, so generated code can read them. Files the run writes to
`/app/output` are pulled back out (via BoxLite's tar download), saved to the
library, and attached to the conversation, and the tool reports their names to
the model. This works for both the ephemeral `sandboxd` backend and the
persistent per-user computer; a computer clears `/app/output` after each run so
it does not re-report the same files.

There is no host-kernel (Podman) execution path. If `sandboxd`/BoxLite is
unreachable the backend **fails closed** rather than silently degrading.

## Storage backends

Persistence sits behind the `chat-store` traits, so the database engine is a
composition-root choice rather than an application dependency:

- **`postgres` (default).** Relational data in Postgres. Best integrity and
  scale.
- **`sqlite`.** A single file, no server; BLOBs/TEXT. Great for local
  development, tests and single-file deployments.

Select with `DB_BACKEND=postgres|sqlite` (plus `DATABASE_URL`). Adding another
engine means writing one more impl of `Store`; application code does not change.
The SQL and migrations are still per-backend — a clean seam, not a free lunch.

## File (object) storage

Uploads sit behind the `chat-store` `FileStore` trait, so the backend is a
composition-root choice:

- **`local` (default).** Files are written to `FILE_STORAGE_DIR` on the host.
  No dependencies, no accounts — ideal for a single replica, a VPS, or a
  Raspberry Pi. This is the recommended default for self-hosting.
- **`s3`.** Any S3-compatible object store, selected with
  `FILE_STORAGE_KIND=s3`. **Required** when more than one replica serves
  uploads, because a pod's local disk is invisible to its siblings.

For a managed setup there are free S3-compatible tiers (limits change, check
before relying on them):

| Provider           | Free tier (approx.)                       | Notes              |
| ------------------ | ----------------------------------------- | ------------------ |
| Cloudflare R2      | ~10 GB, 1M writes + 10M reads/mo, $0 egress | Best managed fit   |
| Backblaze B2       | ~10 GB, egress free up to ~3x stored       | Mature, cheap      |
| Storj              | ~25 GB (account/trial)                     | S3 gateway         |
| IDrive e2          | ~10 GB                                     | Simple             |
| Filebase           | ~5 GB                                      | IPFS-backed        |

To run **entirely free and self-hosted**, the compose file ships a MinIO
service behind the `s3` profile:

```bash
# Start Postgres + MinIO + the bucket-creation helper
podman compose -f deploy/compose.yaml --profile s3 up -d

# Point the API at MinIO
FILE_STORAGE_KIND=s3 \
S3_ENDPOINT=http://localhost:9000 \
S3_BUCKET=rustchat \
AWS_ACCESS_KEY_ID=rustchat AWS_SECRET_ACCESS_KEY=rustchat-secret \
just run
```

S3-compatible stores other than AWS require `S3_ENDPOINT`; path-style
addressing is used automatically. Credentials are read from the standard
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` variables (or an instance
profile), so the same config works on EC2/EKS with an IAM role.

## Attached documents (inline, no embeddings)

Attached documents are **inlined into the prompt**, not embedded. On every
`POST /api/chat` turn, `FileWorkspace::attachment_context` reads the
conversation's attached files and prepends them as a system preamble, bounded at
128 KiB/file and 256 KiB total. Text decoding handles UTF-8 and UTF-16 (LE/BE),
and PDF, DOCX, XLSX, PPTX and HTML are parsed to text; parsing is capped at
25 MiB and 20 s per file. When `OCR_COMMAND` is set, scans, screenshots and
image-only PDFs are recognized as well: the document path is appended to the
command as its last argument, its name is in `OCR_FILENAME`, and the text is
read from stdout. A document that cannot be read is skipped, never an error.
Images are read this way only when the turn's provider is not marked as
serving vision models; a vision provider receives the images themselves (see
[Providers](#providers)).

There is no vector store, chunker or embedder: the RAG/embedding stack was
removed because inlining is exact, needs no extra service, and answers
instantly for the document sizes this product targets.

## Quick start

```bash
# 1. Enter the dev shell (rustc, sqlx, node, podman, just ...)
nix develop

# 2. Configure the environment
cp .env.example .env          # then edit JWT_SECRET / provider keys

# 3. Start Postgres 16 + pgvector (rootless Podman)
just db-up

# 4. Run the API (applies embedded migrations on boot)
just run                      # http://localhost:3080

# 5. (optional) run the frontend
just web-install
just web-dev                  # http://localhost:5173
```

Verify the API is up:

```bash
curl -s localhost:3080/health
```

### Run the full stack with Compose

[`deploy/compose.yaml`](deploy/compose.yaml) builds and runs Postgres (`pgvector`)
+ `chat-server` + the SvelteKit web app. The images come from
[`deploy/docker/rust.Dockerfile`](deploy/docker/rust.Dockerfile) and
[`deploy/docker/web.Dockerfile`](deploy/docker/web.Dockerfile).

```bash

just stack-up                        # podman compose; or just compose="docker compose" stack-up
#   API: http://localhost:3080
#   Web: http://localhost:5173
just stack-logs
just stack-down
```

Base images are fully qualified (`docker.io/...`) so Podman works without an
unqualified-search registry. Override the compose provider with
`just compose="docker compose" stack-up`.

> **Sandbox needs KVM.** `chat-server` calls `sandboxd`, which drives a BoxLite
> server. Start both with the `sandboxd` compose profile; it builds and runs a
> privileged `boxlite` container with `/dev/kvm` passed through. Set
> `SANDBOXD_TOKEN` (mandatory) and, to use an external BoxLite instead, point
> `BOXLITE_URL` at a reachable `boxlite serve`.
>
> **Chat needs a provider.** Register the first account (it becomes admin) and
> configure a provider on the `/setup` page, or create one per user at runtime.
> Providers are BYOK; no provider key is required in the env.

For the target production topology on EKS — node groups, autoscaling signals,
networking and state — see [`docs/eks-topology.md`](docs/eks-topology.md).

`sandboxd` reads its own environment: `SANDBOXD_TOKEN` (**required**),
`SANDBOXD_BIND_ADDR` (`0.0.0.0:3081`), `SANDBOX_BACKEND` (`boxlite`; `gvisor`
selects the gVisor backend), `BOXLITE_URL` (`http://localhost:8100`), optional
`BOXLITE_TOKEN`, and the sandbox spec — `SANDBOX_IMAGE` (`python:3.12-slim`),
`SANDBOX_TIMEOUT_SECONDS` (`30`), `SANDBOX_MEMORY_MB` (`512`), `SANDBOX_CPUS`
(`1`), and `SANDBOX_DISK_GB` (unset — caps the box's writable disk when set).

With `SANDBOX_BACKEND=gvisor`, `runsc` must be installed and each image
unpacked into `GVISOR_IMAGE_ROOT` (`/var/lib/rustchat/gvisor/images`) as
`<GVISOR_IMAGE_ROOT>/<image>`. The persistent-computer endpoints
(`/v1/computers*` and `/v1/workspaces*`) are BoxLite-only and return
`501 Not Implemented` under gVisor.

Egress is denied by default. Set `SANDBOX_NETWORK=true` to allow outbound
traffic, and optionally `SANDBOX_EGRESS_ALLOW` (comma-separated IPv4, IPv4 CIDR,
hostname or `*.wildcard`, at most 10) to restrict it to an allow-list; other
hosts are sinkholed and the box logs the block. `SANDBOX_EGRESS_ALLOW` requires
`SANDBOX_NETWORK=true`. The policy applies to every box `sandboxd` creates,
including per-user computers, so it is a per-node/per-deployment control.

With `COMPUTER_WORKSPACE` (default), each computer mounts a durable managed
volume (named from the user) at the box working directory, so a workspace
survives the box being stopped, reaped or re-provisioned on another node.
Pausing stops the box and snapshots its disks; resuming starts it again, and a
lost box is transparently re-created from the volume. An explicit `DELETE
/api/computers/me` removes the volume too.

With `COMPUTER_WARM_POOL`, blank boxes are pre-provisioned per node to hide
BoxLite cold start; a new computer takes a warm box instead of booting one.
Pool ownership is recorded in the `computer_pool` table and every box is named
`rustchat-pool-*`/`rustchat-computer-*`, so the reaper's reconciliation pass can
list each node's boxes and reclaim any box this deployment no longer owns — a
box orphaned by a crash, a lost placement race, or a pool turned off. The pool
size per node is exposed to admins at `GET /api/admin/computers`.

`GET /api/conversations/{id}/messages` is cursor-paginated. It returns up to
`limit` messages (default 50, max 200) in oldest-first order, ordered by
`(created_at, id)` so pages are stable even when timestamps collide. Pass
`before=<message_id>` to fetch the page of messages older than one you already
have, or `after=<message_id>` for the page newer than it; with neither, the most
recent page is returned. The two cursors are mutually exclusive.

`/api/chat` streams `text/event-stream` events: `meta` (the assistant
`message_id` and a `resume_path`), `delta` (incremental text, with the byte
offset as the SSE event `id`), `thinking` (reasoning/thinking text from a
reasoning model, as `{"text": ...}`), `error`, and a terminal `done`. Agent
turns also emit `tool_call` and `tool_result` events.

The assistant reply is streamed and checkpointed to the database as it is
generated, and generation runs in a detached task, so a client disconnect does
not lose the reply. A client can reconnect with `GET
/api/messages/{id}/stream`, sending `Last-Event-ID` to resume from where it
stopped. Live rejoin works within a single replica; reconnecting to a different
replica replays the persisted content and reports an interruption if generation
was still in flight.

Providers are configured at runtime, not from the environment. An admin can
create an **instance-wide** provider (`global: true`, `providers.user_id IS
NULL`) with or without an API key. When it has no shared key, each user supplies
their own via `PUT /api/providers/{id}/credential` (personal, encrypted at
rest); key resolution prefers the caller's credential over the provider's own
key. `GET /api/providers` returns `has_key` per provider so the UI can prompt
for the missing key, and admins are never forced through provider setup.

A provider carries a `vision` flag, set from the provider form (or `POST` /
`PATCH /api/providers`), for endpoints that serve models accepting image input.
A turn on a vision provider sends the conversation's attached images to the
model as OpenAI-style `image_url` parts (up to 4 images, 4 MiB each) instead of
reading them as text; a provider without the flag never receives an image part,
and the image is read as text or skipped as usual.

Which models a caller may use is an allow-list layered three deep: the
deployment-wide `MODEL_ALLOWLIST`, a provider's own `allowed_models` (set from
the provider form or `POST`/`PATCH /api/providers`), and an account's
`allowed_models` (an admin sets it with `PATCH /api/admin/users/{id}`). Each
layer narrows the provider's cached model catalog, and a chat turn asking for a
model outside the result is rejected with a 400 instead of being forwarded to
the provider. An empty allow-list means "no restriction"; a layer that excludes
every model fails closed. `GET /api/models` and
`GET /api/providers/{id}/models` return the narrowed catalog.

`POST /api/files` takes JSON: `{ filename, content_b64, conversation_id? }`.
Uploads are written under `FILE_STORAGE_DIR` into the caller's personal
library; when `conversation_id` is set the file is also attached to that
conversation. The response returns the created `file` record. The filename is
sanitized and the MIME type is sniffed from the bytes rather than taken from the
client; uploads larger than `UPLOAD_MAX_BYTES` are rejected, and when
`UPLOAD_SCAN_COMMAND` is set an external scanner runs over every upload.

Registration mails a confirmation link and, with `REQUIRE_EMAIL_VERIFICATION`
on, an account cannot use the API until the address is confirmed; `POST
/api/auth/resend-verification` sends a fresh link. `POST /api/auth/password-reset`
mails a reset link, and `POST /api/auth/password-reset/confirm` sets the new
password and signs every existing session out. Both tokens are single-use,
expire (24h verification, 1h reset), are stored only as a SHA-256 hash, and the
request endpoints always answer 204 so they cannot be used to probe which
addresses exist. `MAIL_SEND_COMMAND` names the sendmail-compatible command that
delivers them (see `.env.example`); with no command set, links are not sent and a
warning is logged. The `/verify-email` and `/reset-password` pages consume the
links, and both flows are recorded in the audit trail.

Authenticated routes expect `Authorization: Bearer <jwt>`. Registering and
logging in return a short-lived access token plus a rotating `refresh_token`;
call `POST /api/auth/refresh` with the latter to mint a new pair. Refresh tokens
are stored hashed, rotate on every use, and replaying a revoked token revokes
the whole user's session family. `/api/auth/*` and `/api/chat` are per-IP rate
limited; admin actions and auth/sandbox events are written to an audit trail
shown in the `/admin` console.

Sign-ins are also locked per account: `LOGIN_MAX_FAILURES` consecutive failures
lock the account for `LOGIN_LOCKOUT_SECONDS`, a success clears the count, and an
admin clears a lock early with `PATCH /api/admin/users/{id}` `{"unlock": true}`
(lock-outs and unlocks are audited). Passwords are rejected when they are shorter
than eight characters or match the bundled list of the most commonly breached
passwords, wherever they are set: registration, admin creation and reset.

Programmatic clients can use an API key instead of a session token: mint one at
`POST /api/api-keys` (the plaintext is returned once and only its SHA-256 hash
is stored) and send it as `Authorization: Bearer rck_...`. A key is limited to a
subset of its owner's permissions through `scopes`, may carry an expiry, and
authenticates the same routes as a session token. `GET /api/api-keys` lists the
caller's keys, `DELETE /api/api-keys/{id}` revokes one, and both creation and
revocation are audited while `last_used_at` tracks use.

### Permissions

Authorization is scope-based. Each route requires a `(scope, action)` pair where
the action is `view`, `use` or `manage`, and the scopes cover `conversations`,
`messages`, `agents`, `mcp_servers`, `providers`, `files`, `chat`, `sandbox`,
`computers`, `models`, `api_keys`, plus the admin-only `admin_users`, `admin_audit`,
`admin_computers` and `admin_providers`. Roles map onto that model: `admin`
holds every permission, while `user` holds `view`/`use`/`manage` on their own
resources and `use` on `chat`/`sandbox`. Ownership is still checked per row, so
a `user` can only touch their own resources. `GET /api/me` returns the caller's
granted `permissions` (a list of `{scope, action}`), and admin routes are
enforced by the `admin_*` scopes rather than a bare role check.

### Example: register + chat

```bash
TOKEN=$(curl -s localhost:3080/api/auth/register \
  -H 'content-type: application/json' \
  -d '{"email":"me@example.com","password":"a-long-passphrase-42"}' | jq -r .token)

CID=$(curl -s localhost:3080/api/conversations \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"title":"hello"}' | jq -r .id)

curl -N localhost:3080/api/chat \
  -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d "{\"conversation_id\":\"$CID\",\"content\":\"explain monads\"}"
```

## Database & migrations

Migrations live per backend and are applied automatically on server start
(`sqlx::migrate!`):

- [`migrations/postgres/`](migrations/postgres) — `0001_init.sql` creates the
  core tables (users, providers, agents, mcp_servers, conversations, messages,
  files); a later migration drops the legacy `embeddings` table now that RAG is
  gone.
- [`migrations/sqlite/`](migrations/sqlite) — the equivalent SQLite schema
  (UUIDs as BLOBs, timestamps as RFC3339 TEXT); a later migration drops the
  legacy `chunks` table.

## Status

Scaffolded and under active development. The sandbox split (`chat-server` ->
`sandboxd` -> BoxLite) and the OpenAI-compatible streaming path are functional.
With `COMPUTERS_ENABLED`, a user's `execute_code` tool calls run on their own
long-lived computer (one live box per user, placed via the `computers` registry)
rather than a shared throwaway box. With `COMPUTER_WORKSPACE`, the computer
remounts a durable workspace volume so its files outlive the box, and pausing
snapshots it. `COMPUTER_WARM_POOL` pre-provisions blank boxes to hide cold
start; ownership is durable and reconciled against each node, so boxes orphaned
by a crash are reclaimed.

With `MCP_ENABLED`, each user can register Model Context Protocol servers
(`POST /api/mcp-servers`) and their tools are exposed to the agent runtime,
namespaced `mcp__<server>__<tool>`. Both transports are supported: `stdio`
spawns a local command, while `http` speaks Streamable HTTP (JSON or SSE
responses) to a URL. Connections are opened on demand, cached across turns,
reconnected if they drop, and shut down after `MCP_IDLE_TTL_SECONDS` idle.

A `stdio` server can instead run **inside the sandbox** by setting `sandbox:
true` (optionally `sandbox_image`), so an untrusted server never touches the
host: `chat-server` opens a bidirectional exec over `sandboxd` (which proxies
BoxLite's attach WebSocket) and bridges the server's newline-delimited JSON-RPC
across the boundary. The box is a fresh microVM with no host filesystem, and
its egress follows the deployment's sandbox policy; it is destroyed when the
connection closes or the server goes idle.
